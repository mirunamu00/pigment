# 하네스 전수 점검 보고서 (2026-10-18)

범위: `packages/harness` 전체(5.2천 줄), 평가 기준(`docs/harness/*`), 에이전트·스킬 지침, 지금까지 쌓인 실행 데이터
(평가 41회, 에이전트 실행 193회). 생성은 한 번도 돌리지 않고 기존 데이터만 분석했다.

## 2. 구조적 문제 (원인별)

### A. 점수 체계
1. **척도가 무의미하다.** 7개 항목 0~5점이지만 실제로는 3/4만 쓴다. 평균 임계값 4.0은 "모든 항목 4점"과 같아서, 리뷰어가 아무 항목에서나 3점 하나를 주면 떨어진다.
2. **심각도 구분이 없다.** "화면이 깨짐"과 "캡션 문구가 표 숫자를 반복함"이 같은 무게로 3점을 만든다.
3. **리뷰어 지침이 끝없는 흠 찾기를 유도한다.** "통과시키지 말고 문제를 찾아라", "모든 문제를 빠짐없이 나열하라" → 매 라운드 새 흠 3~6개.
4. **리뷰어 프롬프트가 고정돼 있지 않다.** 라운드마다 오케스트레이터(나)가 손으로 써서, "새 기준을 찾지 말라" 같은 문구가 들어갔다 빠졌다 했다. 평가 조건 자체가 매번 다르다.
5. **재현성 확인이 없다.** 같은 결과를 두 번 채점해 일치하는지 본 적이 없다.

### B. 자동 검사
6. **색·폰트·모서리 준수율은 변별력이 없다** (위 데이터). 남겨도 되지만 품질 지표로 보면 안 된다.
7. **리뷰어가 눈대중으로 재는 것들이 자동으로 잴 수 있는 것들이다.** 이번에 반복된 지적 대부분이 측정 가능했다: 글자 잘림(말줄임 없는 overflow), 요소 간 간격(48px), 나란한 패널의 윗선·아랫선, 구분선 중복, 표 첫 열 정렬, 같은 그림 반복, 레이아웃 빈 공간. LLM이 "±3px"로 추정하며 흔들렸다.
8. **레퍼런스 유사도는 사실상 미구현**이다.

### C. 과적합
9. **예시 앱 4종이 시험지이자 교재다.** 리뷰 지적 → 프롬프트 수정 → 같은 4종으로 재평가. 분리된 검증용 앱이 없다.
10. **과적합을 막는 장치가 없다.** 템플릿 본문에 예시 앱의 상품명·화면명·test id·문구가 들어가도 아무 경고가 없다.
11. **단어 수 한도(7,500)가 규칙을 밀어낸다.** 예시 앱 맞춤 규칙이 늘어나며 일반 규칙과 점검 항목이 잘렸고, 그게 다음 라운드의 퇴보로 이어졌다(Graphite rc.1, rc.5, rc.8). 또 공백만 줄여 단어 수를 맞추는 우회가 생겼다.

### D. 비용·절차
12. **비용 상한·추적이 없다.** 실행마다 `agent-meta.json`에 비용이 기록되는데 어디서도 합산·경고하지 않는다. 반복 횟수 제한도 스킬 문서에만 있고 코드에는 없다.
13. **"통과 후 계속 고치기"를 막는 장치가 없다.** 통과한 후보가 있어도 다음 라운드가 자동으로 이어졌다(Graphite rc.8·rc.9, Night rc.7).
14. **배포된 버전 수정이 새 템플릿 개발과 같은 절차**라서, 작은 버그 하나에도 전체 재생성이 든다.

### E. 실험실 환경 (사용자 환경과의 차이)
15. **실험실 에이전트는 스크립트 실행·파일 삭제·측정을 못 한다.** 그래서 프롬프트의 "측정해서 표로 보고" 단계를 12번 중 대부분 건너뛰었다(평가 불가 상태가 반복). 실제 사용자 에이전트는 할 수 있다.
16. **상태 캡처의 공백이 계속 반복된다.** 실제 로딩 요청 없음, 모션은 첫 경로만, 고정 헤더가 전체 페이지 캡처 중간에 찍힘. 매 리뷰가 "알려진 공백"으로 따로 처리한다.
17. **분석 단계에서 추론한 값을 눈으로 확인하는 절차가 없다.** Night Cartridge의 누런 "낮" 테마가 견본 없이 글로만 승인됐다.

### F. 테스트
18. **평가·생성·배포 로직에 테스트가 없다.** 하네스 테스트 16개는 검증기·캡처만 다룬다. 이번 세션에 고친 버그(폰트 이름 오판, 캡처 중단, 정의 안 된 변수)는 모두 실행 중에 발견됐다.

## 3. 개선안 (우선순위 순)

### P0 — 비용과 판정부터
1. **판정을 "심각도별 발견 목록"으로 바꾼다.** 리뷰어는 7개 항목 점수 대신 발견마다 다음을 적는다.
   - 등급: 차단(화면 깨짐, 기능·접근성 문제, 레퍼런스 정체성 상실) / 주요(시그니처 레시피 위반, 레퍼런스보다 확실히 나쁨) / 경미
   - 표본 수, 근거 이미지, 레퍼런스 근거
   - 통과 조건: **차단 0개, 반복되는 주요 0개.** 경미는 기록만 하고 판정에 쓰지 않는다.
   - 7개 항목 점수는 설명용으로만 남긴다(척도를 쓰고 싶으면 "1~3: 미달/충족/탁월"처럼 3단계로).
2. **리뷰어·작성자 프롬프트를 하네스가 생성한다.** `pnpm harness critic-brief <ref>`가 고정 템플릿으로 리뷰어 지시문을 만든다(대상 경로, 표본, 이전 판정, 비교 대상 자동 채움). 오케스트레이터가 손으로 쓰지 않는다.
3. **비용 추적·상한을 코드에 넣는다.**
   - `evaluate`가 그 버전의 누적 에이전트 비용·실행 수를 보고서에 표시한다.
   - `generate`는 템플릿별 예산(예: 새 템플릿 $150, 업데이트 $60)을 넘으면 `--over-budget` 없이는 거부한다.
   - 반복 횟수 상한도 코드로 강제한다.
4. **통과하면 멈춘다.** 통과한 후보가 나오면 `generate`는 같은 버전 계열의 새 rc를 만들 때 경고하고 확인을 요구한다. 남은 경미 사항은 목록으로만 보여준다.

### P1 — 측정을 자동으로
5. **레이아웃 자동 검사를 shoot에 추가한다** (리뷰어 눈대중 대체, 보고용 → 일부는 게이트).
   - 잘린 텍스트(`scrollWidth > clientWidth`이고 `text-overflow` 없음)
   - 나란한 형제 요소의 윗선·아랫선 차이
   - 연속된 구분선(사이에 내용 없는 border 두 개)
   - 겹치는 텍스트 요소, 화면 밖으로 나간 요소
   - 같은 SVG/이미지의 반복(해시 비교)
   - 각 섹션 사이 간격 분포(토큰 값에서 벗어난 간격 비율)
6. **변별력 없는 준수율 지표를 고친다.** 색 준수는 "의미 토큰(semantic)" 색만 기준으로 하고, 면적이 큰 색이 토큰 밖이면 실패하게 한다. 지표는 남기되 임계값을 실제 분포에 맞게 재설정한다.
7. **레퍼런스 유사도를 실제로 구현한다.** 에이전트 결과물(styles.json) vs 레퍼런스(styles.json)의 팔레트·글자 크기·간격·모서리 분포 거리. 게이트가 아니라 "너무 멀다(정체성 상실)·너무 같다(복제)" 경고로.

### P1 — 과적합 방지
8. **검증용 앱을 분리한다.** 예시 앱 4종(개발용)은 리뷰 지적과 프롬프트 수정에 쓰고, **별도 2종(검증용)**은 최종 확인에만 쓴다. 검증용 앱의 지적은 프롬프트에 직접 반영하지 않고, 같은 원칙이 개발용 앱에서도 깨질 때만 반영한다.
   - 검증용 예: 랜딩/마케팅 페이지, 문서 사이트(사이드바+본문) — 구조가 4종과 다른 것.
9. **과적합 린트를 검증기에 넣는다.** 예시 앱 데이터에서 고유 단어를 뽑아(상품명, 프로젝트명, 화면 제목, test id, 고정 문구) 템플릿 본문에 나오면 경고한다. "예시 앱 이름 대신 일반 용어로" 안내 포함.
10. **작성자 지침에 "일반화 규칙"을 추가한다.** 리뷰 지적은 "어떤 일반 원칙이 빠졌나"로 바꿔 반영하고, 특정 화면·상품을 언급하지 않는다.
11. **단어 수 한도를 토큰 기준으로 바꾸고, 핵심/세부를 나눈다.** agent.md 본문(원칙·레시피·규칙)과 컴포넌트 상세를 분리해, 컴포넌트는 별도 파일(스펙 URL·MCP로 제공)로 둔다. 본문이 잘려 나가는 일을 막는다.

### P2 — 실험실 환경 정비 (사용자 환경과 맞추기)
12. **측정 도구를 제공하거나, 프롬프트에서 측정 보고를 뺀다.** 실제 사용자 에이전트는 측정할 수 있으므로 `pigment-snap --measure`(요소 크기·간격 JSON)를 주는 게 현실에 가깝다. 아니면 프롬프트의 "측정 표" 요구 자체를 없앤다(자동 검사 5번이 대신함).
13. **반복되는 캡처 공백을 고친다.** 예시 앱에 로딩 상태 경로 추가(지연 응답 모의), 고정 헤더는 전체 캡처 전에 정적으로 바꿔 찍기, 모션은 모든 경로에서 짧게.
14. **분석 확인 단계에서 추론 값을 견본으로 보여준다.** check-analysis가 추론한 색 모드가 있으면 견본 이미지를 만들고, 스킬이 체크포인트에서 반드시 보여주게 한다.

### P2 — 테스트
15. **evaluate(표본·게이트)·publish(carry-from·갤러리 선택)·generate(표본 id)·validate(새 린트)에 단위 테스트를 추가한다.** 실행 없이 픽스처로 검증.

## 4. 예상 효과
- **비용:** 통과 후 계속 고치기 금지 + 선별 후 확인 + 예산 상한으로, 이번 세션 같은 누적(배포 후 수정에 $700+)은 구조적으로 막힌다. 새 템플릿 하나는 대략 선별 2~3회($60~90) + 확인 1회($40) 수준.
- **판정 안정성:** 3/4 이진 점수 대신 차단/주요 개수로 판정하면, 경미한 흠 하나로 떨어지는 일이 없어진다. 자동 측정이 늘어 리뷰어 편차가 줄어든다.
- **일반화:** 검증용 앱 분리와 과적합 린트로 "예시 앱만 잘 되는 프롬프트"를 걸러낸다.

## 5. 결정이 필요한 것
1. 판정 방식 전환(점수 → 심각도별 발견 목록, 통과 = 차단 0·반복 주요 0)에 동의하는지
2. 예산 기본값(새 템플릿 / 업데이트)
3. 검증용 앱 2종 추가 여부와 종류(추가하면 개발 비용이 들지만 1회성)
4. 실험실 측정 도구 제공(사용자 환경에 맞춤) vs 프롬프트에서 측정 보고 제거
5. agent.md 핵심/세부 분리(컴포넌트 상세를 별도 파일로)

## 6. 적용 결과 (같은 날, 사용자 위임으로 기본값 결정)

5번 항목은 사용자가 "알아서" 하라고 해서 아래 기본값으로 정했다. 생성·평가 실행은 한 번도 하지 않았다.

| 개선안 | 적용 | 위치 |
| --- | --- | --- |
| 1. 심각도별 판정 | 리뷰어는 발견마다 차단/주요/경미 + 표본 수 + 스펙 원인 여부를 적는다. 통과 = 차단 0, 반복(2+표본)·스펙 원인·단일 표본의 주요 0. 점수는 설명용. 옛 점수 파일은 옛 기준으로 판정 | `schema` `CriticFinding`, `evaluate.ts` `judgeCritic` |
